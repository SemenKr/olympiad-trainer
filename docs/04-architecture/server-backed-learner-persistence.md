# Server-backed Learner Persistence v1

Progress has one PostgreSQL source after a browser's legacy import succeeds. Practice drafts, unfinished sessions and the latest completed Summary remain browser-local. The server issues an anonymous 256-bit token in a persistent `HttpOnly`, `SameSite=Lax` cookie (`Secure` in production); only its SHA-256 hash is stored. The browser never supplies a learner ID. Normal identity resolution never creates a learner. A fresh browser initializes explicitly before learner operations; missing identity with existing local work remains blocked rather than importing that work into a replacement learner. Account linking remains unavailable. Optional saved recovery codes can restore access to the same learner in another browser under the [Identity & Recovery contract](learner-identity-recovery-v1.md); recovery revokes the previous browser credential and does not transfer unsent drafts from another device.

`learners` holds three explicit factual evidence snapshots: separate sock/parrots three-slot sections sharing one sequence for guarantee, separate I-08/G5S-1 three-slot sections sharing one sequence for impossibility, and a three-slot enumeration bucket for `pages-without-digit-one`. The enumeration bucket retains the latest correct checkpoint without hints, correct checkpoint with hints, and incorrect checkpoint. Adaptive closure lives in the four-column `practice_adaptive_target_usage` ledger, independently of bounded evidence and prunable completed history. Migration 0014 removes the obsolete target-specific learner booleans. `practice_finish_receipts` stores `(learner_id, session_id, contribution_hash)` for durable retry detection, with nullable mode and Pack identity. These tables do not store Progress groups, conclusions, mastery, answers, or recommendations. `/progress` derives three learner-facing capability sections—in guarantee, impossibility, enumeration order—after structural validation and canonical checkpoint reverification, followed by the existing recent Practice history and the shared next-work projection.

Before `/progress` reads or a contributing Finish writes, the browser submits its exact legacy Progress bytes (or `null`) once. The server accepts the guarantee-only v1 shape, the two-bucket v2 shape, and the three-bucket v3 shape (`guarantee`, `impossibility`, and `enumeration`), verifies all retained facts against canonical checkpoint answers, and imports the snapshots as a baseline. Older v1 and v2 inputs receive an empty enumeration bucket; no enumeration observations are inferred during import. It hashes the original bytes. The same hash retries safely; different nonempty bytes after import conflict. Invalid or unverifiable bytes produce an error. The browser removes the local value only after acknowledgement and only while it still equals the imported bytes. A fresh browser with the same cookie and no local bytes can read the existing server evidence.

For an eligible Finish, the browser stores an immutable request under the Practice Web Lock before sending it. New version-2 requests contain stable session ID, exact contributions and completed episode facts; target closure is derived from the validated adaptive episode, including skip/hint-only Finish. Historical pending payloads retain their exact unversioned form, adaptive marker semantics and hash recipe. In the authenticated learner-row-locked transaction, receipt-first replay returns the original acknowledgement without modifying evidence/history/closure; changed payloads conflict. New Finish appends eligible evidence, saves completed history and Journey award, writes the receipt and inserts target usage atomically. Rollback leaves no partial state. Only after acknowledgement does browser finalization clear unfinished state and save latest Summary under the same lock; failure retains pending bytes for identical retry.

Before any legacy import, an already-pending Finish written by the previous browser-local implementation is recovered under the Practice Web Lock. Ordinary Practice restore may restore its unfinished snapshot, but cannot consume the marker; autosave and new sessions remain blocked while it exists. The resulting Progress bytes are imported as baseline while the old pending marker and bytes remain available for a lost response or failed import. Only after acknowledgement are the marker and matching bytes removed. This Finish does not also create a new server receipt or duplicate the contribution.

The existing browser-local Practice episode determines whether a checkpoint is eligible. The server validates contribution shape and rechecks its checkpoint option and outcome against protected content. This v1 does not independently attest main-answer correctness, hint exposure or solution exposure; those facts remain client-attested until Practice itself moves server-side.

`/progress` imports before reading, then reads PostgreSQL only. Database, import or verification failures show the existing retryable error; no stale local fallback or raw evidence reaches the UI. Empty evidence is shown only after a successful verified read.

## Setup and deployment

Use a managed PostgreSQL database for each local, preview and production environment. Set server-only `DATABASE_URL` to its runtime pooled connection string. Set `DATABASE_MIGRATION_URL` to a direct connection string when the provider requires one for DDL. Run `pnpm db:migrate` explicitly once during environment setup or deployment before serving this version; migrations never run per request. The committed SQL is in `db/migrations/`. Do not expose either URL through `NEXT_PUBLIC_` variables. Local integration tests use a separate `DATABASE_TEST_URL` database.

## Learning Path v1

[Learning Path v1](learning-path-v1.md) adds nullable `pack_id` to Finish receipts via migration 0011. Only validated Pack Finish writes the derived identity, atomically within the existing transaction. No cursor/table/backfill or altered contribution hash. Reads validate and deduplicate learner-scoped receipt IDs; legacy null IDs remain unknown and retries do not annotate them.

[Adaptive Practice v1](adaptive-practice-v1.md) uses migration 0014 for normalized durable target usage. It backfills only proven flags/checkpoints or exact validated surviving adaptive episode/receipt pairs, asserts coverage and drops six obsolete flags in the runner transaction. Unknown legacy targets are never inferred. Imported target checkpoints create sessionless usage, not receipts. Usage survives history pruning and establishes returning status, while exploration still requires a durable non-Review Practice Finish. See the adopted v1 contract for migration, immutable replay and controlled production cutover requirements.

## Recovery hardening

Routine authenticated reconciliation of the same store, owner/generation and binding preserves an existing active storage lease when no identity switch is pending. Suspension, corrupt state, changed bindings and identity transitions still invalidate captured leases.

Server-backed Practice Finish reports confirmed completion, unknown acknowledgement, incomplete local reconciliation after acknowledgement, or a blocked attempt. An uncertain outcome preserves the exact pending request; retry uses authenticated payload-idempotent replay. Reload restores the unfinished snapshot for that replay when local finalization was interrupted, rather than treating local completion bytes as server acknowledgement. Learner feedback distinguishes uncertainty from acknowledged persistence with incomplete browser reconciliation.

Home makes a verified unfinished episode available for Resume without waiting for the previous Summary. A failed secondary Summary verification is announced separately with retry; it cannot replace Resume or offer a fresh session. Unfinished verification failures remain blocking and retryable. Local creation, saves and clears confirm the resulting storage bytes before reporting success; failed writes retain the existing recoverable snapshot where available.

## Identity Boundary foundation (slice 2)

[Identity & Recovery v1](learner-identity-recovery-v1.md) slice 2 introduces server-only authenticated context: learner UUID, browser-token hash and credential generation. Migration `0012_learner_identity_boundary.sql` adds nonnegative generation (initially zero) and required server expiry. Existing rows retain their UUID, token hash and all learning records; expiry is migration time plus 730 days, matching the existing cookie lifetime. New initialization sets cookie/server expiry to 730 days from issue. Resolution does not refresh expiry.

`resolveLearnerFromCookie` is lookup-only. Missing, malformed, unknown, expired or rotated credentials fail without replacement or cookie mutation. Explicit initialization refuses an existing invalid cookie. A client initialization gate precedes learner effects and serializes fresh creation across tabs with a Web Lock; if the cookie is absent but existing learner storage is present, it preserves the bytes and stops. This gate is first-use wiring, not recovery UI or proof of identity. An entirely cleared browser remains indistinguishable from a genuinely new browser.

Every persistence operation accepts authenticated context instead of a bare learner UUID. The shared ownership transaction locks the learner row, rechecks token hash/generation, then checks expiry against PostgreSQL `clock_timestamp()` after lock acquisition. All learning reads/writes complete under that lock, including Progress/import/Finish/history, Review/Journey/Learning Path, Knowledge Support, and Simulation. Resolving a context earlier cannot bypass later revocation. Simulation assistance checks no longer bypass identity for a missing cookie; unrelated static Practice content remains independent of Simulation as before.

At the foundation stage described in this section, Recovery was not yet implemented or enabled. Subsequent work implemented client owner envelopes, expected-context transport, stale-tab switch barriers, the code lifecycle and recovery UX. Recovery is now released to controlled canonical-host production; see the [current production release record](../05-development/recovery-production-runbook.md#current-production-release-record). Other environments remain fail-closed unless explicitly configured and enabled. Identity/recovery migrations must precede application deployment; application versions that lack revocation/context enforcement cannot safely coexist with enabled Recovery.
