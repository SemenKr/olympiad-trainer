# Server-backed Learner Persistence v1

Progress has one PostgreSQL source after a browser's legacy import succeeds. Practice drafts, unfinished sessions and the latest completed Summary remain browser-local. The server issues an anonymous 256-bit token in a persistent `HttpOnly`, `SameSite=Lax` cookie (`Secure` in production); only its SHA-256 hash is stored. The browser never supplies a learner ID. A lost cookie currently means a new learner; account linking and cross-device recovery are later work.

`learners` holds two explicit factual three-slot evidence snapshots, one for the guarantee checkpoint and one for the impossibility checkpoint. `practice_finish_receipts` stores `(learner_id, session_id, contribution_hash)` for durable retry detection. Neither table stores Progress groups, conclusions, mastery, answers, or recommendations. The existing interpretation functions derive the two learner-facing capability cards after structural validation and canonical checkpoint reverification.

Before `/progress` reads or a contributing Finish writes, the browser submits its exact legacy Progress bytes (or `null`) once. The server accepts the guarantee-only v1 shape and the two-bucket v2 shape, verifies all retained facts against canonical checkpoint answers, and imports the snapshots as a baseline. It hashes the original bytes. The same hash retries safely; different nonempty bytes after import conflict. Invalid or unverifiable bytes produce an error. The browser removes the local value only after acknowledgement and only while it still equals the imported bytes. A fresh browser with the same cookie and no local bytes can read the existing server evidence.

For an eligible Finish, the browser first stores an immutable, bounded request under the Practice Web Lock: stable session ID, exact factual contributions and the local snapshot/results needed for finalization. Practice saves stop while this request is pending. Every retry sends the stored session ID and contributions, even if in-memory Practice state has changed. In one PostgreSQL transaction, the server locks the learner row, checks the receipt, appends to the appropriate explicit buckets with the next sequence, inserts the receipt and commits. An identical retry succeeds without appending again; a changed contribution for the same session conflicts. Only after server acknowledgement does the browser finalize latest Summary and clear unfinished Practice under the same lock. A failed server call leaves unfinished Practice and the request in place; local finalization failure also retains the request for an identical retry.

Before any legacy import, an already-pending Finish written by the previous browser-local implementation is recovered under the Practice Web Lock. Ordinary Practice restore may restore its unfinished snapshot, but cannot consume the marker; autosave and new sessions remain blocked while it exists. The resulting Progress bytes are imported as baseline while the old pending marker and bytes remain available for a lost response or failed import. Only after acknowledgement are the marker and matching bytes removed. This Finish does not also create a new server receipt or duplicate the contribution.

The existing browser-local Practice episode determines whether a checkpoint is eligible. The server validates contribution shape and rechecks its checkpoint option and outcome against protected content. This v1 does not independently attest main-answer correctness, hint exposure or solution exposure; those facts remain client-attested until Practice itself moves server-side.

`/progress` imports before reading, then reads PostgreSQL only. Database, import or verification failures show the existing retryable error; no stale local fallback or raw evidence reaches the UI. Empty evidence is shown only after a successful verified read.

## Setup and deployment

Use a managed PostgreSQL database for each local, preview and production environment. Set server-only `DATABASE_URL` to its runtime pooled connection string. Set `DATABASE_MIGRATION_URL` to a direct connection string when the provider requires one for DDL. Run `pnpm db:migrate` explicitly once during environment setup or deployment before serving this version; migrations never run per request. The committed SQL is in `db/migrations/`. Do not expose either URL through `NEXT_PUBLIC_` variables. Local integration tests use a separate `DATABASE_TEST_URL` database.
