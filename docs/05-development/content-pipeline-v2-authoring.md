# Content Pipeline v2 — authoring

The server-only `problem-catalog.ts` remains authoritative. This branch retains its 60 approved problems and Packs A–R. The request describes 63 and A–S, but those three problems and Pack S are absent from the requested base branch; this workflow does not add or reconstruct them. Existing definitions stay in the catalog. New definitions use one small TypeScript module per problem and an explicit import in `new-problem-modules.ts`.

## Create and review a problem

1. From a dedicated feature branch, run `pnpm content:new <lowercase-kebab-case-id>`. The command rejects malformed and known IDs and creates `server/problems/drafts/<id>.ts`. It contains only an ID, grade, subject and empty title/statement. It has no answer or source data and is not imported by the catalog, so it cannot appear in learner content. Do not add draft imports.
2. Confirm source and usage rights. Complete the mathematics and references with human review under the [v1 authoring rules](content-pipeline-v1.md). Move the draft to `server/problems/<id>.ts`; export a complete object with `satisfies ProblemDefinition` from `../problem-catalog`. Include assessment, three ordered hints, solution, and original and official-solution references. The training interpretation is separate from source facts. An incomplete module should fail typecheck or content validation.
3. Import that module in `server/new-problem-modules.ts` and append it once to `NEW_PROBLEM_DEFINITIONS`. This is the only registration step. Do not add it to browser metadata manually. Registration alone makes the definition addressable through the server catalog, so only register a reviewed task when an approved entry point is ready. For ordinary Practice, choose an approved Pack with exactly three distinct problem IDs and its own learner-safe name; adding a Pack requires a separately approved tuple and any needed database/rollback compatibility work. If the task belongs to another approved entry point, wire that entry point explicitly. Do not silently modify an existing Pack tuple.
4. Run `pnpm content:generate`, then `pnpm content:check`, `pnpm typecheck`, and applicable repository checks. `content:generate` writes `ui/browser-problem-metadata.generated.ts` from the catalog. `content:check` validates definitions and the independent `content-identities.json` guard, checks exact generated-file freshness, and runs authoring plus Resume/History storage regressions. Review the generated diff. It includes only IDs, title, ordered hint IDs, solution ID and visible option IDs; it must not include answers, hint or solution text, checkpoint correctness or provenance.
5. Have an independent reviewer inspect the exact diff and a human verify mathematical correctness, source correspondence, adaptation and rights. Only then expose the entry point. Append reviewed identities to `content-identities.json` manually as an independent append-only guard; never generate or rewrite the baseline to make validation pass. Existing identities and ordered Pack tuples remain immutable without a separately adopted compatibility plan.

The fixture tests create drafts in temporary directories and compose a new definition in memory. They do not register a learner problem. This authoring automation does not solve browser rollback compatibility for a future Pack, and the later structural SQL migration remains separate work. No Production or Neon action is part of these commands.
