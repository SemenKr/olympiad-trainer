# Adaptive v1 expand–migrate–contract release

This procedure supersedes the original 0014 cutover procedure for PR #98. Production is at 0013 with six legacy learner flags. Preview already applied immutable 0014. Never edit or replay 0014. Record deployment, migration, snapshot and control IDs privately; do not record credentials, bypass links, learner identities or Finish payloads.

## Schema and application compatibility

From 0013, the runner applies corrected 0018 (four-column closure ledger, validated backfill, six flags retained), 0016 (temporary legacy-write capture), and forward repair 0019 in **one connection and transaction**. A lock on learners and completed episodes prevents writes between backfill and trigger installation. On a database with applied 0014, the runner applies 0016 and 0019. Existing 0015+0016 environments receive only 0019; applied 0014–0017 files remain unchanged. A frozen source basis may contain hints: 0018/0019 validate its corresponding hinted or unhinted slot while retaining canonical-answer, shape, sequence and contradiction checks. A database already contracted by 0017 needs no bridge repair. Its deferred episode trigger captures a valid old episode even when pruning deletes it before a receipt insert; it checks for the matching receipt at commit. Old flags and version 1/2 checkpoint evidence also close proven targets. Unknown identities stay unknown. Ledger closure never reopens on pruning.

The expansion supports overlapping database writers, but an immutable old application cannot decode a new v2 Finish request. The reviewed v1 build with `ADAPTIVE_RELEASE_MODE=rollback` is the only post-v1 application rollback candidate: it suppresses automatic adaptive entry while retaining v2 and historical Finish decoding, immutable receipt replay, local pending state, recovery and ledger closure. Do not route v2 clients to `ae8976a`. The contract migration 0017 removes capture hooks and six flags only after every old writer has retired; it is not a v1 cutover step. Run it separately with `MIGRATION_PHASE=contract` and `RELEASE_OLD_WRITERS_RETIRED=confirmed` under new approval.

## Cutover

1. Before any merge, confirm PR #98 is the reviewed commit and CI is green, identify the exact production project/database, and freeze manual production deployments and credential synchronization. Complete the writer inventory, including database logins, external/control-plane writers and all four Recovery cron schedules. Confirm the old Preview bypass is retired, browser smoke access works, the recovery procedure is available, and the production deployment/alias sequence is known and guarded. Record the pre-expansion state with `node scripts/inspect-release-db.mjs before`: production must have 13 migrations, six flags and no ledger. Keep migration-owner credentials outside deployments. **Do not merge PR #98 until the additive schema is ready, the limited v1 runtime and protocol-compatible rollback are ready, and the production deployment/alias sequence has been verified.** A merge to the configured Production branch triggers a Vercel production deployment; ordinary CI does not wait for the schema migration. Keep Preview on its isolated Preview database.
2. Under separate approval, begin a short, bounded writer pause. Activate and verify a project-wide maintenance deny covering canonical domains and every deployment/generated alias, including authenticated and bypass traffic. Initially permit no application hostname; verify the operator can inspect the protected deployment through normal authenticated access without opening learner routes to the public. Preserve Deployment Protection and the Recovery rate limit; do not use a broad WAF bypass. Pause all four Recovery cron schedules and every inventoried external/control-plane writer. Confirm the deny and pause are effective before continuing. If any writer cannot be paused or ingress/operator access cannot be verified, abort before snapshot or migration.
3. Create a fresh whole-database Neon snapshot while the writer and cron pause is still verified. Before expansion, verify snapshot readiness, source branch/endpoint, ID, retention, creation time and LSN where available; record non-sensitive counts. Supply genuine `RELEASE_WRITER_DENY_ID` and `RELEASE_RECOVERY_POINT_ID` evidence IDs to the production migration guard. The guard checks that IDs are present; operators must retain evidence that the writer pause and recovery point actually occurred. Keep both requirements unchanged. If the snapshot is not ready or its source/identity cannot be verified, end the pause safely and abort before migration.
4. Under the migration approval, run the existing runner for the 0013 production history with bounded session timeouts: set `PGLOCK_TIMEOUT=5000` and `PGSTATEMENT_TIMEOUT=120000` (milliseconds) for the runner process, then run `MIGRATION_PHASE=expand node scripts/migrate-db.mjs`. These node-postgres startup settings bound individual lock waits to 5 seconds and statements to 120 seconds without changing the runner. Do not retry automatically or increase limits in place. A lock timeout, statement timeout, deadlock, connection loss, unexpected schema state or failed transaction is an abort: allow the runner to roll back, verify the database remains at its prior migration history, inspect read-only, and schedule a newly approved attempt. Do not manually split 0018, 0016 and 0019. Require `node scripts/inspect-release-db.mjs expanded` to verify the ledger and six legacy flags before resuming any writer. Keep the 0014 path (0016 + 0019), 0015 + 0016 path (0019 only), and already-contracted 0017 path unchanged; never edit or replay applied migrations.
5. Once expanded-schema verification passes, end the temporary writer pause, resume the compatible old application and its Recovery schedules, and confirm normal service. **Permanent legacy credential retirement and migration 0017 are later, separately approved steps; neither is required for this additive expansion.** Keep the 0016 bridge and all six flags until every old writer is permanently retired.
6. Prepare the limited v1 runtime and the protocol-compatible rollback on the expanded schema. Use distinct least-privilege roles and no migration-owner credentials. Verify ledger grants, configuration, readiness and exact commits. Keep the rollback login disabled until needed. Before starting the controlled v1 deployment, re-enter a separately approved short maintenance window: deny every hostname except the exact selected canonical smoke hostname from the verified operator source IP, pause the Recovery crons and other writers again, and verify the rule. Project-wide host matching must include all canonical and generated/deployment aliases; Vercel previously reassigned a generated alias despite auto-assignment being disabled. Do not treat `--skip-domain` as a safety control. If any unexpected alias is reachable outside the deny or the operator cannot reach the smoke candidate, stop and restore the prior alias/ingress state under maintenance.
7. Only after steps 1–6 are satisfied may PR #98 be merged to trigger the ordinary GitHub → Vercel Production release. Keep maintenance active while Vercel deploys the exact reviewed v1 commit. Verify READY state, commit, runtime role/configuration and the actual canonical and generated alias assignments. Use the single selected canonical production domain. Through normal authenticated browser flow, smoke legacy import → Journey, Home/Progress parity, Resume, historical pending Finish retry, and a synthetic v2 skip/hint-only Finish with durable closure. Check Recovery, Review and Simulation boundaries, migration shape, role access and errors. No action-ID scraping. If deployment, alias verification or smoke fails, keep ingress denied, do not reopen; route only to the prepared protocol-compatible rollback on the expanded schema, then re-verify. **Public ingress and cron resumption require a separate explicit release approval after successful smoke.**
8. After that separate approval, reopen the selected canonical domain and resume Recovery cron and other writers against v1. Keep the old application/database credential set temporarily available for the compatible phase, but do not use it as a rollback target after v2 requests reach v1. Permanently retire the old credentials only after all old writers have been retired and verified; then run 0017 under its own approval with `MIGRATION_PHASE=contract` and `RELEASE_OLD_WRITERS_RETIRED=confirmed`. After real learner or Recovery writes are acknowledged, never restore the pre-expansion snapshot over them; fix forward or roll back application code only to the protocol-compatible build on the expanded schema.

## Failure boundaries and approvals

Before expansion commits, any timeout or failed migration must abort without retrying in place; verify transaction rollback and the prior schema before scheduling another approved attempt. Because additive capture supports old and new Finish writes, old deployments may resume after expanded-schema verification while permanent credential retirement is deferred. Keep 0016 capture and legacy flags until old writers retire. Before v1 deployment, reapply the verified maintenance/cron pause and keep it through authenticated smoke. After v1 exposure, only the protocol-compatible build may receive v2 clients. Crossing the data rollback boundary means reopening public ingress or resuming real learner, Recovery or other non-synthetic writes: after that, never restore the pre-expansion snapshot over acknowledged state. Migration 0017 remains a separate, gated contract action, permitted only after old-writer retirement is proven and separately approved; after 0017, old code is permanently schema-incompatible.

Production remains **NO-GO** until writer inventory and pause, truthful guard evidence IDs, fresh verified snapshot, atomic expansion/readback, compatible old-app resume, limited v1 and rollback readiness, guarded Git/Vercel deployment sequence, authenticated smoke and separate public-release approval are complete. Remaining operational prerequisites include verified operator access and source IP, removal of the obsolete Preview bypass, a tested project-wide deny covering generated aliases, control-plane/external writer pause, cron pause/resume, candidate role grants, snapshot readiness and the bounded-timeout migration window. No step authorizes production mutation by itself. Permanent credential retirement and 0017 remain later, separately approved gates.
