# Adaptive v1 expand–migrate–contract release

This procedure supersedes the original 0014 cutover procedure for PR #98. Production is at 0013 with six legacy learner flags. Preview already applied immutable 0014. Never edit or replay 0014. Record deployment, migration, snapshot and control IDs privately; do not record credentials, bypass links, learner identities or Finish payloads.

## Schema and application compatibility

From 0013, the runner applies corrected 0018 (four-column closure ledger, validated backfill, six flags retained), 0016 (temporary legacy-write capture), and forward repair 0019 in **one connection and transaction**. A lock on learners and completed episodes prevents writes between backfill and trigger installation. On a database with applied 0014, the runner applies 0016 and 0019. Existing 0015+0016 environments receive only 0019; applied 0014–0017 files remain unchanged. A frozen source basis may contain hints: 0018/0019 validate its corresponding hinted or unhinted slot while retaining canonical-answer, shape, sequence and contradiction checks. A database already contracted by 0017 needs no bridge repair. Its deferred episode trigger captures a valid old episode even when pruning deletes it before a receipt insert; it checks for the matching receipt at commit. Old flags and version 1/2 checkpoint evidence also close proven targets. Unknown identities stay unknown. Ledger closure never reopens on pruning.

The expansion supports overlapping database writers, but an immutable old application cannot decode a new v2 Finish request. The reviewed v1 build with `ADAPTIVE_RELEASE_MODE=rollback` is the only post-v1 application rollback candidate: it suppresses automatic adaptive entry while retaining v2 and historical Finish decoding, immutable receipt replay, local pending state, recovery and ledger closure. Do not route v2 clients to `ae8976a`. The contract migration 0017 removes capture hooks and six flags only after every old writer has retired; it is not a v1 cutover step. Run it separately with `MIGRATION_PHASE=contract` and `RELEASE_OLD_WRITERS_RETIRED=confirmed` under new approval.

## Cutover

1. Confirm exact reviewed commit/CI, production target identity, all credential holders and external writers, four Recovery cron dependencies, runtime grants including ledger DML, and snapshot/restore capacity. Keep migration-owner credentials outside deployments. Confirm authenticated-browser smoke and old Preview bypass cleanup. Test the actual maintenance rule on the Vercel plan. Preserve Recovery rate limiting and Deployment Protection.
2. Under separate approval, run `node scripts/inspect-release-db.mjs before` against production: 13 migrations, six flags, no ledger. Record aggregates. Run `MIGRATION_PHASE=expand node scripts/migrate-db.mjs` using the production migration-target gates. The short learner/episode write lock is the only expected interruption. Require `node scripts/inspect-release-db.mjs expanded` to pass: 0018+0016+0019, flags retained, ledger present. A failed transaction leaves 0013; inspect before retry. Never manually split expansion, capture and repair.
3. Activate and verify maintenance ingress denying canonical and all old generated hosts, including authenticated/bypass access. Pause crons and direct/external writers. Wait at least 360 seconds after the last admitted request, longer for any other writer. Inspect active and prepared transactions. Retire every legacy credential copied into immutable deployments, restart/drain production compute and prove direct and pooled fresh authentication rejection plus zero old sessions. If any old writer survives, stop. The expansion capture hooks protect writes that occurred before the fence.
4. Create a fresh whole-database Neon snapshot after drain and credential retirement, before v1 exposure. Verify readiness, branch, ID, retention, timestamp/LSN where available, and counts. This is a recovery point only while no real later write has been acknowledged.
5. While maintenance is active, deploy exact v1 and protocol-compatible rollback production candidates with distinct least-privilege roles, no admin credentials. Verify READY, commit, configuration and actual canonical/generated alias mapping after **each** deployment. Stage B1 observed a generated alias move despite `autoAssignCustomDomains:false`; `--skip-domain` is not a safety control. Do not stage in the live project before maintenance unless a separately proven alias-safe method exists. Keep rollback login disabled until needed.
6. Assign the intended canonical aliases to v1 under maintenance. Through normal authenticated browser flow, smoke legacy import → Journey, Home/Progress parity, Resume, historical pending Finish retry and a synthetic v2 skip/hint-only Finish with durable closure. Check Recovery, Review and Simulation boundaries, migration shape, role access and errors. No action-ID scraping. Reuse existing CI/review and Preview evidence.
7. Obtain the explicit reopening decision, then release public ingress and resume background writers against v1. Keep old credentials retired. Rollback after real traffic means maintenance, drain, alias switch to the protocol-compatible rollback build on the expanded database, smoke, then reopen. Never restore the pre-v1 snapshot over acknowledged learner or Recovery writes.

## Failure boundaries and approvals

Before expansion commit, verify transaction rollback and 0013; old application may continue. After expansion but before v1 exposure, old code may continue with capture hooks, unless its credential was retired. After v1 exposure, only the protocol-compatible build may receive v2 clients; fix schema failures forward. After 0017, old code is permanently schema-incompatible.

Production remains **NO-GO** until separate approvals cover expansion, maintenance/cron pause, credential retirement and compute restart, fresh snapshot, deployment/alias changes, synthetic smoke and reopening. Also close the remaining evidence gaps: exhaustive writer inventory, actual maintenance rule behavior, authenticated browser smoke and old bypass status, alias behavior under maintenance, and recovery capacity at cutover. No step here authorizes production mutation by itself.
