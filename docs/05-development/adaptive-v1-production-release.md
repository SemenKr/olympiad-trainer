## 1. Prepare candidates and operator access

1. Confirm reviewed PR SHA/CI. Freeze Git/manual production deployments and integration credential synchronization; disable **Auto-assign Custom Production Domains**, then verify readback. Inventory every production credential holder, database login role, endpoint, external writer and cron dependency. Inspect credentials securely in place, reporting only role/host/target identity. The Stage A deployment inventory covers 234 deployments but detailed environment-key inspection covers only the newest 100; resolve any additional credential roles before release. Provider-managed roles are not application credentials and must not be rotated indiscriminately.
2. Establish two fresh SQL-created runtime roles, `ot_runtime_v1` and `ot_runtime_rollback`, initially `NOLOGIN`, with independently generated secrets handled only through secure operator input. Do not use Neon API role creation that grants `neon_superuser` membership. Both roles must have no superuser, database/role creation, replication, RLS bypass, owner membership or ability to assume the owner role. Check effective permissions, including inherited/PUBLIC grants, not just role flags. The migration owner remains operator-only.

   ```sql
   CREATE ROLE ot_runtime_v1 NOLOGIN NOSUPERUSER NOCREATEDB
     NOCREATEROLE NOREPLICATION NOBYPASSRLS;
   CREATE ROLE ot_runtime_rollback NOLOGIN NOSUPERUSER NOCREATEDB
     NOCREATEROLE NOREPLICATION NOBYPASSRLS;
   GRANT CONNECT ON DATABASE neondb TO ot_runtime_v1, ot_runtime_rollback;
   GRANT USAGE ON SCHEMA public TO ot_runtime_v1, ot_runtime_rollback;
   ```

   Set passwords separately without echo/logging. Grant SELECT/INSERT/UPDATE/DELETE on the explicitly enumerated existing application tables, excluding `schema_migrations`; grant USAGE/SELECT on application sequences where needed. No schema CREATE, ownership, migration-marker write or broad future default grants. Check every existing runtime SQL path against these grants. Migration 0014's new ledger receives an explicit grant after migration. [Neon role behavior](https://neon.com/docs/manage/roles).

3. Build the exact reviewed v1 SHA in the Production environment with `--skip-domain`, bound only to the v1 runtime role. Separately stage baseline `ae8976a` with the rollback runtime role. Verify READY, exact SHA, environment and absence of canonical aliases; builds must not require runtime database login. If a build requires database access, stop rather than enabling v1 against schema 0013. Remove owner/admin `DATABASE_MIGRATION_URL` and all alternative owner-credential aliases from future candidate environments; the operator supplies migration credentials outside Vercel. Verify integrations cannot reinject them. Keep required Recovery/HMAC/cron settings, with values private. Do not alter old immutable deployments as a substitute for credential fencing. [Staging/promotion](https://vercel.com/docs/deployments/promoting-a-deployment).
4. Have functioning authenticated browser access for the supported learner smoke. ## 2. Maintenance, credential fence and drain

1. Install and read back a highest-priority maintenance deny covering all old generated URLs, aliases and Preview deployments as well as canonical production ingress. Permit only the exact staged candidate host AND designated operator source IP; no broad operator-IP exception that can reach old deployments. Preserve existing Recovery rate limiting and protection. Verify representative canonical, old production, old Preview and authenticated-owner requests are denied. Verify the candidate-only exception works. This WAF behavior has not been exercised in production during Stage A; any failed verification is a stop gate.
2. In Project Settings → Cron Jobs, use **Disable Cron Jobs** to pause all four Recovery cleanup schedules; read back the disabled state. Pause every direct/external writer and trusted control-plane SQL operator too. Verify no new cron invocation or deployment starts; pausing HTTP ingress alone is insufficient. Keep these paused through smoke and the rollback decision. [Supported cron controls](https://vercel.com/docs/cron-jobs/manage-cron-jobs).
3. Retire every inventoried legacy production login password, including the owner password copied into immutable deployments. Store the replacement owner credential only with the operator. Keep both staged runtime roles `NOLOGIN`. Verify role/credential changes completed and that integration synchronization has not rebound candidate credentials. Rotation prevents new authentication but does not end existing sessions.
4. Wait at least 360 seconds after the last admitted request (the inspected Hobby Function limit is 300 seconds, plus margin); use a longer bound if any external writer requires it. Inspect active/idle-in-transaction sessions and prepared transactions. Restart the production compute explicitly, under the approved maintenance window, to sever existing direct and pooled sessions. Do not rely on ordinary `pg_terminate_backend` privileges against the old Neon owner. Wait for restart completion and successful operator reconnect, not just API acceptance. [Function limits](https://vercel.com/docs/functions/limitations), [Neon compute operations](https://neon.com/docs/manage/endpoints/).
5. Verify changed server start time, old open handles disconnected, no old application transactions/sessions (identify operator sessions separately), and zero prepared transactions. Check fresh direct AND pooled authentication with each retired credential fails with an authentication rejection; a timeout/network failure is not proof. Verify both new disabled roles reject login. Production currently reports `pooler_enabled=false`; still test every URL form actually embedded in old deployments. If any old credential authenticates, stop. Permanent credential retirement is the authoritative old-writer fence even if an old URL or protection bypass remains reachable.

Verify snapshot readiness, ID, branch, recovery timestamp/LSN where provided, retention deadline and aggregate data counts. Six-hour history alone is not the release checkpoint. The snapshot must capture the retired-password state, not reintroduce old credentials on rollback. The latter references the private fence packet containing WAF rule, credential-retirement and restart evidence. These fields are operator attestations, not automatic platform verification; never invent an ID to pass the guard.
3. Run `node scripts/inspect-release-db.mjs before`: require PASS, exactly 13 migrations, six flags, no adaptive ledger or receipt adaptive column, and correct target identity. Retain aggregate counts. Run `node scripts/migrate-db.mjs` once with identical target settings. SQL/backfill/assertions/bookkeeping run on one connection and transaction; the advisory lock coordinates migration runners, not application writers. Never rewrite an applied migration.
4. Run `node scripts/inspect-release-db.mjs after`: require PASS, 14 migrations, zero obsolete flags, ledger present, stable learner/receipt/episode aggregates. Separately verify ledger keys/FKs/checks and aggregate closure coverage. Any failure after commit keeps maintenance active.

## 4. Smoke, promotion and reopening

Use designated synthetic state only while real traffic and background writers are fenced. Through normal browser flow verify legacy import → Journey, Home/Progress parity, stale recommendation handling and safe Resume. Exercise a retained historical pending Finish/immutable retry and a new skip or hint-only Finish with durable closure; bound Review/Simulation/Recovery checks to the release risk. Do not clear existing local state. Prior application review/tests and Preview isolation are reused; this smoke checks production role grants, wiring and origin-dependent behavior.

Promote the exact staged production deployment while maintenance remains active. Verify canonical aliases reference its ID, then narrowly adapt the operator exception to canonical hosts for cookie/origin checks without permitting old hosts. Verify error rates, persistence and migration state. [Promotion](https://vercel.com/docs/deployments/promoting-a-deployment) does not roll back the database.

Only after successful smoke and the explicit rollback decision, reopen public ingress and resume cron/external writers against the new deployment. Treat opening real traffic or resuming non-synthetic background/security writes as crossing the data rollback boundary. Keep old passwords permanently retired and automatic production domain assignment disabled until a later deliberate release. Preserve the Recovery ceiling and Deployment Protection.

## Failure and rollback boundaries

- Before migration commit: verify the transaction rolled back and schema/data remain 0013. Activate the staged baseline candidate using its fresh rollback role, never an old immutable deployment carrying a retired password. Do not restore a pre-drain checkpoint over successfully committed old-user writes.
- After commit, before ANY real learner, Recovery or non-synthetic background/security write: maintain ingress denial; disable/retire the v1 runtime credential, drain and restart before restore. Restore the entire post-fence snapshot with `finalize:false`; inspect the restored branch for 0013, six flags, expected aggregates and disabled roles before finalizing. Finalization reassigns/restarts computes and swaps names: verify endpoint/branch bindings, target identity and owner access afterward. Recheck all retired credentials and effective grants; restoration must not reopen old writers. Enable only the rollback runtime role, select the staged baseline candidate, perform operator smoke and reopen by approval. Only explicitly recorded synthetic smoke writes may be discarded.
- After any acknowledged real write or non-synthetic background/security change: keep/restore maintenance and fix forward on 0014. Whole-database rollback would lose data or revive revoked recovery state. Application-only rollback is unsafe because old code expects removed columns. A new recovery/data-reconciliation plan requires separate approval.
