# Adaptive v1 — production release procedure

Applies to PR #98 and migration `0014_adaptive_target_usage.sql`. This procedure is an attended release, not an automatic CI migration. It does not authorize a release. The operator records the exact project, commit, deployment, database branch, timestamps and evidence IDs in private operational notes. Do not copy connection strings, cookies, learner IDs or request bodies into notes or logs.

## Release prerequisites

1. PR head, independent review and CI must still match the intended code. Verify the intended Production environment settings and disable **Auto-assign Custom Production Domains** before a `main` push or merge; a normal Git deployment can otherwise become public during migration. Stage the exact reviewed commit as a production build with `--skip-domain` and verify READY, SHA and production environment. A successful Preview build is not the staged production build.
2. Have a verified project-wide ingress Deny mechanism covering every production alias, generated deployment URL and Preview environment, including authenticated owners and cron traffic. Inspect the active rule and its ordering/bypasses; test representative old alias, old generated URL and old Preview URL. Do not assume a canonical-domain swap, Vercel Authentication or the migration advisory lock blocks old writers. Pause direct DB writers and scheduled jobs as well.
3. Agree on a maintenance window. After the Deny rule is active, wait for already-admitted functions and database transactions to end. Inspect bounded active-session counts and ensure no old writer or `idle in transaction` remains; do not infer quiescence merely from quiet HTTP logs. Record the live Deny rule ID and timestamp.
4. Create and verify a whole-database recovery point **after** writer drain and **before** migration. Record its ID and retention deadline. Six-hour restore history without a snapshot is not a durable release checkpoint. Confirm that restore permissions and a return-to-service procedure exist before proceeding.

If any prerequisite is missing, stop with the ingress Deny active. The operator may reopen the old deployment only while the old schema remains intact.

## Migration and cutover

1. Use the direct production connection, never the pooled URL. Supply `MIGRATION_TARGET=production`, `DATABASE_MIGRATION_URL`, `PRODUCTION_DATABASE_HOST`, `PRODUCTION_DATABASE_NAME`, `RELEASE_RECOVERY_POINT_ID` and `RELEASE_WRITER_DENY_ID` from the verified facts above. These IDs are operator attestations, not automated proof that Vercel traffic is blocked or a snapshot is restorable.
2. Run `node scripts/inspect-release-db.mjs before` with those target settings. It uses a read-only transaction and must report PASS, 13 migrations, six flags and no ledger or receipt adaptive column. Stop if production differs or the target identity does not match the inspected Neon branch.
3. Run `node scripts/migrate-db.mjs` once with the same target settings. The runner checks target identity before opening the connection and executes all migration SQL, assertions and migration bookkeeping on one connection and transaction. Do not modify an already applied migration.
4. Run `node scripts/inspect-release-db.mjs after`; require PASS, 14 migrations, zero old flags, ledger present and stable aggregate learner/receipt/episode counts. Inspect the ledger constraints and sample aggregate closure coverage without exporting learner data. Failure after commit leaves maintenance active for investigation.
5. Promote the staged **production** deployment. Keep public ingress denied. Allow only a narrow operator path to the new deployment and verify all canonical aliases route to its ID; retain denial of all old generated URLs and old Preview URLs. No old application version may reach the contracted schema.
6. Smoke with a disposable learner: Home/Progress parity, a stale suggestion, safe Resume, a historical pending Finish and immutable retry, a new skip/hint-only Finish with durable closure, plus a bounded Review/Simulation/Recovery check. Inspect aggregate error rates and migration/receipt counts. Do not clear existing users' local snapshots or pending Finish. Restore normal public ingress only after smoke passes and old deployment URLs remain fenced. Keep automatic production domain assignment disabled until later `main` builds are intentionally promoted.

## Failure and rollback

- Before the migration transaction commits: inspect the rolled-back schema and migration list, then reopen the old deployment if they still match 0001–0013.
- After commit but before any real learner or Recovery write: under maintenance, restore the **entire** database to the recorded point, verify the old schema and data aggregates, then return the old production deployment. Restoring schema alone is insufficient.
- After any acknowledged real write: keep ingress closed and fix forward on the new schema. Restoring an earlier database would lose acknowledged Finish data and may revive revoked credentials. Do not use Vercel application-only rollback; the old server expects six columns removed by 0014.

The operator must verify the active firewall configuration in Vercel Dashboard or an authenticated CLI. The Firewall connector returned 404 during preparation, so this runbook does not claim that an effective Deny rule currently exists. New code and this procedure alone do not change the production release status from NO-GO.
