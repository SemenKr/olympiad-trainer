## Runtime and operator contract

`POST /api/internal/db-binding` is the only accepted method. Production platform flags, the live `VERCEL_DEPLOYMENT_ID`, a matching operator-supplied deployment ID, exact generated `VERCEL_URL` origin and Host, no query/body, a valid dedicated bearer, and an absolute window of at most ten minutes must all match. Aliases, Preview, missing platform variables and expired/malformed configuration deny access before pool creation. Next.js supplies a non-null stream for even a bodyless POST: after authentication, the route accepts only a null body or a stream completed without any chunks within 250ms. Any data, error or unfinished stream is denied before target/pool access; cancellation is not awaited. The deployment ID header is an operator assertion compared with the runtime identity, not a substitute for independently verifying that identity in Vercel.

The three temporary configuration values are `DB_BINDING_DIAGNOSTIC_TOKEN_SHA256`, `DB_BINDING_DIAGNOSTIC_ISSUED_AT` and `DB_BINDING_DIAGNOSTIC_EXPIRES_AT`. `node scripts/db-binding-operator.mjs` generates a dedicated 32-byte random bearer and emits only its SHA-256 verifier and ten-minute UTC window for secure candidate-scoped provisioning. Production receives the verifier, **never the raw bearer**. Neither CRON_SECRET nor a learner credential is used. After non-secret deployment/rollback confirmations, the helper emits reviewed browser source containing only the verifier, window and pinned identities. It then permits one explicit bearer reveal through `/dev/tty` on a private alternate terminal screen for manual transcription into a native browser prompt. The bearer never enters stdout/stderr, console source, shell arguments, URLs, clipboard or persistent storage. Unsupported/noninteractive terminals stop. Do not run through a terminal recorder, remote session, screen sharing, screenshot tool or tracing proxy. Browser prompts are visible text, not masked password fields; private display/input is required. The helper clears the alternate screen on normal completion/error; abrupt process termination or terminal-specific scrollback/recording can defeat visual clearing. Clearing is not a guarantee of memory erasure. If these controls cannot be established, stop before generating a bearer.

Pool acquisition waits at most two seconds; a late acquired client is destroyed. This cannot cancel an already pending connection attempt in the unchanged app pool. Each SQL call has a 2.5-second client timeout; after `BEGIN READ ONLY`, transaction-local statement/lock/idle-in-transaction timeouts are set to 2s/500ms/3s. The bounded SELECT returns booleans only, then ROLLBACK; errors destroy the connection instead of returning uncertain transaction state to the pool. No migration runner, learner initialization, DDL, DML or COMMIT is invoked. These bounds are not a whole-platform availability guarantee. The browser POST has a 12-second network deadline and treats timeout as failure without retry.
