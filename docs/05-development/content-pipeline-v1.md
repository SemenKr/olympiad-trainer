# Content Pipeline v1

The local server catalog contains 63 Grade 5 mathematics problems (60 sourced adaptations and three original visual problems); the learner-safe registry contains 19 ordinary Practice Packs, A–S. Pack S is technically integrated but pending human mathematics and age-suitability approval before release. Its owner distribution/credit approval of 2026-10-19 is recorded with exact scope and limitations in the [Visual Reasoning dossier](../02-research/visual-reasoning-v1.md#owner-distribution-and-credit-decision--2026-10-19); rights for the 60 sourced adaptations remain unresolved. Repository TypeScript remains the authoring format. No content is imported or published by validation.

## Authoring

1. Inspect `src/modules/practice/server/problem-catalog.ts` and the relevant research/source audit before editing. Use a feature branch. Keep factual provenance, adapted learner content, interpretation and training hints distinct.
2. For maintenance, edit an existing definition in place. Preserve its problem ID, response kind, option IDs/order, ordered hint IDs, solution ID and optional checkpoint ID. Saved learner episodes and reveal requests depend on these identities. Wording and answer corrections still require human mathematical review.
3. For an explicitly approved addition, follow an existing `ProblemDefinition` and register it once in `PRACTICE_PROBLEM_DEFINITIONS`. Choose new stable lowercase kebab-case IDs. Supply a nonempty statement, supported assessment, three progressive hints (focus, strategy, next-step) and a protected training solution. Sourced provenance (legacy absent kind or explicit `vsosh`) retains factual original/official-solution PDF references with positive page and task numbers and `training-adaptation` solution kind. Original provenance requires explicit `original`, authorship, truthful rights note, matching subject/grade and an existing safe repository-relative research dossier; its solution kind is `original-explanation`, and all official-only metadata is forbidden. Human approvals remain documented release gates; nonempty evidence strings do not clear them. Numeric answers are canonical nonnegative integer strings; set answers contain distinct known option IDs. Do not infer difficulty from official numbering.
4. When approved scope includes a new Pack, add its learner-safe name and exactly three distinct existing problem IDs to `PRACTICE_PACKS` in `application/completed-practice-episode.ts`. Order is part of identity. Do not change an existing tuple: Resume and History rely on it.
5. Run `pnpm content:validate`, then relevant tests and `pnpm verify`. CI also runs the dedicated validation command. Errors identify the problem/Pack and failed contract. Typecheck complements validation for authored TypeScript; this workflow is not an untrusted JSON importer.
6. Obtain independent code review and explicit human verification of mathematical correctness, source correspondence, adaptation accuracy and source/usage rights before publishing content. Automated checks do not establish these facts or fetch/verify source availability.

## Identity protection and limits

Pack S appends three identities and one ordered tuple to the guard without changing any prior entry. Its learner-safe snapshot metadata is also appended in `ui/practice-session-storage.ts`; response kind, hint/solution identities and titles must match the catalog. Original media must have matching original problem authorship/dossier, valid static presentation and no sourced URL/page/crop. Both provenance branches retain their own validation; unknown/mixed kinds fail. Dossier existence is checked by authoring validation, not by learner requests.

Forward migration `0022_original_visual_pack_receipts.sql` extends only the receipt Pack ID constraint through S and follows 0021 in the shared base migration plan. Apply it before any separately authorized Pack S release. Existing A–R/NULL receipts and both supported adaptive histories remain compatible; no browser snapshot migration, adaptive registration or progress backfill is introduced. See the [local implementation and release gates](visual-reasoning-v1-implementation.md).

Public attribution and the minimal per-source human rights review process are documented in [Content Sources & Attribution v1](content-sources-attribution-v1.md). Attribution does not satisfy the publication rights gate; unresolved usage remains unresolved.

`server/content-identities.json` records the original 42 problem identities and 12 ordered Pack tuples, plus the eighteen adopted Content Expansion problem identities and six additional ordered Pack tuples. Validation compares each baseline entry against the complete raw registration list before lookup can conceal duplicate IDs. It rejects missing or changed identities, duplicate IDs/tuples, broken Pack or expected-option references, invalid answer contracts, hint order, empty support content and malformed provenance. Tests also resolve every hint and solution through the existing protected reveal functions and verify learner projections.

The baseline is a review guard, not tamper-proof storage. Do not regenerate it to silence errors. Add reviewed new entries manually when adopting content; retain all prior entries. An intentional identity migration requires a separately approved compatibility plan for saved state, History and adaptive references. Editing the baseline and content together can bypass the guard and must receive explicit review. Validation permits additions without redefining the original inventory; inventory-count tests document this initial baseline and should be deliberately updated only when adopting new baseline entries.

Answers, unopened hints and full solutions stay server-only. The validator imports the catalog type only; the executable validation test mocks `server-only` solely within Vitest. Runtime projections, adaptive selection, Resume, Finish, History and Progress behavior are unchanged. Existing feature tests remain the regression evidence for those flows. Forward migration `0020_content_expansion_pack_receipts.sql` extends the receipt Pack ID constraint from A–L to A–O without changing existing receipts or completion semantics. It is registered in the shared base migration plan because it depends only on migration 0011 and applies to every supported adaptive schema history. Apply it before releasing Packs M–O. Forward migration `0021_content_expansion_batch_2_pack_receipts.sql` extends the same constraint to A–R; apply it before releasing Packs P–R. Both supported adaptive histories and upgrades from the released 0020 schema are tested. Neither earlier migration is edited; no browser storage migration is needed. See the [Batch 2 human-verification dossier](../02-research/content-expansion-batch-2.md).
